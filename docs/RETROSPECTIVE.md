## 1. 課題の概要

- SDNET2018 の壁面画像（`W/`）を使い、256×256 タイルに「Pコン跡」があるかを判定する2値分類
- 評価は陽性クラスの F1。public（評価画像の約3割）/ private（約7割）に分かれ、最終は private
- 制約: 外部データ・事前学習済みモデル禁止（ImageNet 事前学習も不可）、評価画像への手動ラベル付け禁止
- 学習 10,079 枚（陽性 194 枚 = 1.9%）、評価 8,059 枚。学習・評価は撮影元の写真単位で分割
- 作業時間: 約 11:00〜16:15（約5時間）

## 3. 手法（効いた順）

### 3.1 データ構造の発見：タイルから元写真を復元（最重要の土台）
- ファイル名 `写真ID-タイル番号.jpg` の番号は元写真内の位置（横18×縦14、左上から行優先）
- 並べ直すと元写真を画素単位で完全に復元できた（`src/pcon/data.py`、memmap キャッシュ）
- 陽性タイルの84%は隣接タイルも陽性（穴がタイル境界をまたぐ）。「端に一部だけ写っていても陽性」というルールなので、**対象タイル＋周囲64px（384px）** を入力にした
- 評価画像も同じ方法で復元できる（推論は手元で行い CSV を提出する形式なので問題なし）
- 細部: `_2` が付いたファイルは同じ位置の別名。欠損タイルや重複ファイルもあった。`int("28_2")` が `282` になる Python の仕様で一度誤認したので、正規表現で解析する

### 3.2 難例重み付け（ハードエグザンプルマイニング） → public +0.05
- ベースラインの OOF 予測で間違えやすかったタイルを、サンプリング重み `1 + 5 × 誤差` で最大6倍見せる
- OOF はそのタイルを学習していないモデルの予測なので、公平な難しさの指標になる
- public 0.871 → 0.921。どの seed でも再現した
- 2巡目（重点学習モデルの OOF でさらに重み付け）は悪化。**1巡で十分**

### 3.3 帯状の暗い物体の合成拡張 → 単体 OOF F1 0.882 → 0.892
- Grad-CAM で「モデルは暗い物体の曲線の縁を見ている」ことが判明（靴・排水パイプ・壁の帯で誤検出）
- 30% の確率で、ランダムな角度・幅（25〜90px）・濃さの暗い帯を描き込む（ラベルは変えない）
- 評価画像の帯への誤検出が 9 → 6 件に減少。**最も遅く（15:20）見つけたが、最も効いた施策の1つ**

### 3.4 位置の揺らぎ（jitter）をなくす → AP +0.006、閾値の安定範囲 0.13 → 0.44
- 誤りの大半は「穴がタイル境界にぎりぎりかかるかどうか」の判定
- ±24px の平行移動拡張はタイル境界の位置をぼやけさせていた

### 3.5 閾値の決め方
- OOF の F1 は広い閾値範囲（例: 0.67〜0.91）でほぼ平ら。argmax の1点はたまたまの位置になりやすい
- **平らな範囲の中で、テストの陽性率が学習データの陽性率（1.92%）に一致する閾値**を選ぶ
- public で良かった提出はテスト陽性率 1.90〜1.95% に集中。陽性を控えめにした提出（1.72〜1.76%）は低かった
- 陽性をオーバーサンプリングしているので確率は高めに出る（OOF で 0.5〜0.9 の帯の実際の陽性率は 31%）。閾値は必ず OOF で決める

### 3.6 アンサンブル
- seed 違い・設定違い（jitter 有無、帯の合成有無）の CV モデル＋全データ学習モデルを logit 平均
- 全データ学習モデルは OOF が取れないので、同設定の CV モデルと混ぜてテスト予測にのみ加える
- 貪欲選択は AP 基準（F1 は陽性が少なく不安定）

### 3.7 効かなかったもの

| 施策 | 結果 | 考察 |
|---|---|---|
| ResNet34（大きいモデル） | F1 −0.016, AP −0.04 | 小データ・事前学習なしでは小さいモデルが有利 |
| 周囲128px（縮小して入力） | F1 −0.018 | 縮小で細部が落ちる／20エポックで学習不足 |
| マスク4ch + 拡大縮小 + 20ep | F1 −0.049 | 複数の変更を同時に入れたため原因を切り分けられず |
| 疑似ラベル（評価画像） | F1 −0.012 | 教師モデルの誤りを再学習した可能性 |
| 推論時の拡大（ズームTTA） | 小さい穴の見逃し 10→5 だが誤検出 19→62 | 小さい穴と気泡を区別できていない |
| 隣接タイル・格子配置による後処理（スタッキング） | F1 は上がることもあるが AP は低下 | 閾値の偶然と判断し不採用 |
| 写真外のパディングを平均色に | 改善なし | 端の延長による筋模様は誤検出源だったが、全体では影響小 |

## 4. 検証・評価のノウハウ

- **写真単位の CV が必須**（学習・評価が写真単位で分かれているため）。StratifiedGroupKFold、fold は全実験で固定
- **写真単位ブートストラップ**で、基準との差の95%区間と「改善している確率」を出す（`src/pcon/compare.py`）。陽性が少ない（1fold 30〜40件）ので、0.01〜0.02 の差は誤差になり得る
- **OOF の指標と public の相関**（13提出分）: AP 0.88、F1 0.81、陽性率 0.65。**採否は AP で判断**し、F1 は閾値決めにだけ使う
- **public の F1 は整数の分数に分解できる**（例: 0.9333 = 84/90 → 正解42件、誤り6件）。これで public の陽性数（約45件）や、提出間の差が何件分かを推定できた
- 同点だった提出の差分行は public 外と推定できる。ただし **public/private はタイル単位のランダム分割**だった（写真単位と誤認し、一度誤った結論を出した）。差分は行単位で解釈すること
- public は簡単なタイルが多く、0.92〜0.93 で頭打ちになった。終盤は public では差が見えず、OOF と陽性率で判断した
- 評価画像を見て分かった誤りを手で直すことや、特定の写真だけを狙ったルールは、手動ラベル付けにあたるので行わない

## 5. エラー分析・可視化のノウハウ

- **周辺込みのエラー一覧画像**（`src/pcon/errors.py`）: 見逃し・誤検出を確率順に並べて分類する。今回の分類は、境界ぎりぎり17件、遠くの小さいPコン跡10件、暗い物体6件、写真端のパディングによる模様5件、ピンボケ3件、埋め戻し1件、ラベル抜けの疑い3件
- **元写真に予測を重ねた図**: 写真7131が斜め下からの撮影で、奥の小さいPコン跡だけを見逃していると一目で分かった
- **Grad-CAM**（`src/pcon/inspect_model.py`）: 「何を手がかりにしているか」が分かり、帯の合成という具体策に直結した
- **重みの統計**: 層ごとの標準偏差や0付近の割合、BN の γ を確認。異常はなく、学習の失敗ではなく「学習した手がかりの問題」と切り分けられた
- **データの健全性チェック**（`src/pcon/sanity.py`）: 復元画像と元画像の画素一致、境界の連続性、切り出しの中心、fold の写真単位性、出力の並び、重複画像の予測一致を自動で確認

## 6. 運用・インフラのノウハウ

- **GPU を空けない**: ファイルベースのジョブキュー（`scripts/queue_worker.sh`）で、前のジョブが終わった瞬間に次を開始する。こちらはキューに1行足すだけでよい
- **複数GPU**: WSL の RTX 3060 Ti と研究室サーバの RTX 4090（2本並行）を併用。サーバは `ssh.exe`（Windows 側の SSH 設定）経由で操作し、コードは GitHub 経由で同期、結果は `scripts/sync_lab.sh` で回収した
- **CUDA 版の差**: WSL（ドライバは CUDA 13.3 まで対応）では torch の cu132 版が CUDA 初期化時に segfault したので cu130 を使った。サーバ（CUDA 12.6）では cu126。**新しい環境では `torch.cuda.is_available()` と行列積で最初に確認する**
- **EMA の初期値の罠**: timm の `ModelEmaV3` は `use_warmup=True` と `step` を渡さないと、初期のランダムな重みが残って検証 AP が 0.01（ランダム）になる
- **`pkill -f` の罠**: パターンが自分のシェルのコマンドラインにも一致して、自分自身を殺した。PID を明示するか、`$$` を除外する
- セッションが再接続されたときに、WSL の常駐ジョブが止まったことがあった。`setsid nohup` で起動する
- 提出 CSV は GitHub に置き、ブラウザからダウンロードしてもらう運用にした（手元から直接は採点サイトに上げられないため）
- 提出のたびに `submissions/LOG.md` に OOF・陽性率・public を記録。これが後の相関分析の材料になった

## 7. 反省点（次回への教訓）

1. **モデルが何を見ているかを早く確認する**
   最も効いた帯の合成は、Grad-CAM を見た 15:20 にようやく思いついた。最初のエラー分析（12:35）で靴の誤検出は見えていたので、その時点で可視化していれば2時間以上早く着手できた。**ベースラインができたら、すぐにエラー一覧と Grad-CAM を作る**。

2. **データにない「紛らわしい物体」と「小さい対象」は合成で補う**
   弱点は「暗い物体の縁」と「遠くの小さいPコン跡」で、どちらも学習データに例がほとんどなかった。帯以外の物体（曲線・パイプ状）の合成や、Pコン跡を縮小して貼り付けるコピー&ペースト拡張を、早めに試すべきだった。

3. **1回の実験で変えるのは1つだけ**
   「マスク＋拡大縮小＋20ep」「周囲128px＋20ep」は同時に変えて失敗し、拡大縮小のように効いたかもしれない施策を捨てた。

4. **閾値・陽性率と public の関係を早く見る**
   陽性率とスコアの関係に気づいたのは15時台。最初の数回の提出から陽性率も記録・比較していれば、閾値の方針を早く固められた。

5. **速い GPU を最初から使う**
   4090 は 3060 Ti の約2倍速く、2本並行できた。使い始めは 12:15。最初から使っていれば実験数は約2倍になった。

6. **最終提出の採用ルールを最初に確認する**
   「最高スコアの提出が採用」と分かったのは終盤。この場合、private で効く改善でも public が上がらなければ反映されない。最終の選び方（同点時の扱いを含む）は最初に確認する。

7. **推論の誤りを早く訂正する**
   public/private の分け方を写真単位と誤認し、「難しい写真は private に集中」と一度誤った結論を出した。根拠が間接的な推論は、反例が出たらすぐに撤回する。

## 7.5 中盤（12:30〜14:30頃）に伸び悩んだ原因

OOF F1 が 0.88 前後で約2時間止まった。原因は次の4つ。

1. **原因を確かめないまま、入力やモデルを変えていた（最大の原因）**
   ResNet34・周囲128px・マスク＋拡大縮小・疑似ラベル・重点学習2巡目は、どれも「容量や視野が足りない」という仮説の施策だった。実際のボトルネックは、モデルが「暗い物体の縁」を手がかりにしていたことと、それを正す材料（帯・パイプ・遠くの小さいPコン跡）が学習データにほぼないことだった。容量や視野を増やしても、学ぶ材料がなければ改善しない。
   - 疑似ラベルと2巡目が効かなかったのも同じ理由。**モデルが見落としているものは、モデル自身の予測からは学べない**（自己学習は盲点を補えず、むしろ強化する）
2. **エポック削減と新しい施策を同時に入れていた**
   時間短縮のため 30→20 エポックにしたうえで新しい施策を同時に入れたので、どちらが悪化の原因か分からなかった。効く方向だった拡大縮小や位置揺らぎなしを、一度ここで見送っている。
3. **ぶれやすい F1 中心で判断していた**
   1fold の陽性は30〜40件で、F1 は±0.03程度ぶれる。難例重み付けは OOF F1 で +0.003 に見えたが、public では +0.05 の本物の改善だった。AP の方が public と相関が強いと分かったのは、提出が13本たまってから。
4. **閾値が高すぎて、改善が表に出なかった**
   閾値を F1 の最大点で決めると 0.85〜0.95 と高めになり、テスト陽性率が 1.72〜1.76% と陽性を出し足りていなかった。陽性率に合わせた閾値に変えるだけで public は 0.921→0.933 に上がった。

**教訓**: 伸び悩んだら新しい施策を足す前に、「なぜ間違えるのか」（エラー一覧・Grad-CAM・写真全体での予測の可視化）と「評価や閾値が改善を隠していないか」を確認する。終盤に伸びたきっかけ（Grad-CAM → 帯の合成、変更を1つずつ、閾値の見直し）は、どれも原因を確かめてから手を打つ方向の変化だった。
